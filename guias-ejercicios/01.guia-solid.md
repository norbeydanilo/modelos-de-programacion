# Principios SOLID en Java

## ¿Qué son los principios SOLID?

SOLID es un acrónimo que agrupa **cinco principios de diseño orientado a objetos**, pensados para que el software sea más fácil de mantener, extender y probar. No son reglas de sintaxis (Java no te impide violarlos), son criterios de **buen diseño** que se apoyan directamente en lo que ya conoces de POO: herencia, polimorfismo, interfaces y las relaciones entre clases (asociación, agregación, composición).

- **S** — Single Responsibility Principle (Responsabilidad Única)
- **O** — Open/Closed Principle (Abierto/Cerrado)
- **L** — Liskov Substitution Principle (Sustitución de Liskov)
- **I** — Interface Segregation Principle (Segregación de Interfaces)
- **D** — Dependency Inversion Principle (Inversión de Dependencias)

> **Regla práctica:** SOLID no se aprende leyendo definiciones, se aprende viendo código que los viola, sintiendo el dolor que eso causa cuando el sistema crece, y luego viendo cómo el principio resuelve exactamente ese dolor. Por eso cada sección de esta guía tiene tres partes: **el problema**, **la solución** y **la justificación real**.

Vamos a usar los mismos ejemplos de las guías de POO (`Vehiculo`/`Carro`/`Moto` y `FiguraAbstracta`/`Punto`) para que veas SOLID como una evolución natural de lo que ya construiste, no como algo nuevo y aislado.

## S — Single Responsibility Principle (SRP)

> **Definición:** una clase debe tener **una sola razón para cambiar**. Es decir, debe encargarse de una única responsabilidad.

### El problema

Retomamos `Vehiculo`. Imagina que, además de modelar el vehículo, la clase también se encarga de guardarlo en base de datos y de generar un reporte en PDF:

```java
// MAL: Vehiculo tiene TRES razones para cambiar
public class Vehiculo {

    private String marca;
    private int velocidadMax;

    public Vehiculo(String marca, int velocidadMax) {
        this.marca = marca;
        this.velocidadMax = velocidadMax;
    }

    public void acelerar() {
        System.out.println(marca + " está acelerando.");
    }

    // Responsabilidad 2: persistencia
    public void guardarEnBaseDeDatos() {
        System.out.println("Conectando a la BD...");
        System.out.println("INSERT INTO vehiculos VALUES ('" + marca + "', " + velocidadMax + ")");
    }

    // Responsabilidad 3: generación de reportes
    public void generarReportePDF() {
        System.out.println("Generando PDF con los datos de " + marca + "...");
    }
}
```

**¿Por qué es un problema?** Si cambia el motor de base de datos, tienes que tocar `Vehiculo`. Si cambia el formato del reporte, tienes que tocar `Vehiculo`. Si cambia la lógica del vehículo en sí, también tocas `Vehiculo`. Tres equipos de trabajo distintos (persistencia, reportería, dominio) terminarían modificando el mismo archivo por razones que no tienen nada que ver entre sí, lo que genera conflictos de merge y errores en cascada.

### La solución

Separamos cada responsabilidad en su propia clase:

```java
// BIEN: cada clase tiene una única responsabilidad

// Responsabilidad única: representar el vehículo (dominio)
public class Vehiculo {
    private String marca;
    private int velocidadMax;

    public Vehiculo(String marca, int velocidadMax) {
        this.marca = marca;
        this.velocidadMax = velocidadMax;
    }

    public String getMarca() { return marca; }
    public int getVelocidadMax() { return velocidadMax; }

    public void acelerar() {
        System.out.println(marca + " está acelerando.");
    }
}

// Responsabilidad única: persistencia
public class VehiculoRepositorio {
    public void guardar(Vehiculo v) {
        System.out.println("Conectando a la BD...");
        System.out.println("INSERT INTO vehiculos VALUES ('" + v.getMarca() + "', " + v.getVelocidadMax() + ")");
    }
}

// Responsabilidad única: reportería
public class VehiculoReporteGenerador {
    public void generarPDF(Vehiculo v) {
        System.out.println("Generando PDF con los datos de " + v.getMarca() + "...");
    }
}
```

```java
public class App {
    public static void main(String[] args) {
        Vehiculo carro = new Vehiculo("Renault", 180);

        VehiculoRepositorio repo = new VehiculoRepositorio();
        repo.guardar(carro);

        VehiculoReporteGenerador reporte = new VehiculoReporteGenerador();
        reporte.generarPDF(carro);
    }
}
```

### Justificación real

En un proyecto de verdad, esto no es teoría: es lo que separa una aplicación mantenible de una que nadie quiere tocar. Si mañana el equipo decide migrar de una base de datos relacional a MongoDB, el cambio queda **encapsulado en `VehiculoRepositorio`** y nadie tiene que abrir la clase `Vehiculo` (que probablemente usan otros diez módulos del sistema). SRP es, en el fondo, la razón por la que en arquitecturas reales existen capas separadas (dominio, persistencia, presentación): cada capa cambia por su propia razón, y separarlas evita que un cambio en una rompa las otras.

## O — Open/Closed Principle (OCP)

> **Definición:** las clases deben estar **abiertas a extensión, pero cerradas a modificación**. Se debe poder agregar comportamiento nuevo sin alterar el código que ya funciona y ya fue probado.

### El problema

Retomamos el ejemplo de `FiguraAbstracta` y `Punto` que ya conoces, pero ahora con una clase que calcula áreas usando `if/else` según el tipo:

```java
// MAL: cada vez que aparece una figura nueva, hay que MODIFICAR esta clase
public class CalculadoraDeArea {

    public double calcular(Object figura) {
        if (figura instanceof Circulo) {
            Circulo c = (Circulo) figura;
            return Math.PI * c.getRadio() * c.getRadio();
        } else if (figura instanceof Rectangulo) {
            Rectangulo r = (Rectangulo) figura;
            return r.getBase() * r.getAltura();
        }
        // Si mañana llega Triangulo, hay que agregar OTRO else if aquí...
        return 0;
    }
}
```

**¿Por qué es un problema?** Cada figura nueva obliga a editar `CalculadoraDeArea`, una clase que ya estaba probada y funcionando. Editar código que funciona es la forma más común de introducir errores nuevos en producción (regresiones).

### La solución

Usamos el mismo mecanismo que ya usaste con `FiguraAbstracta`: una clase abstracta (o interfaz) con un método que cada figura implementa a su manera. `CalculadoraDeArea` nunca vuelve a cambiar.

```java
// La abstracción queda CERRADA a modificación
public abstract class FiguraAbstracta {
    public abstract double calcularArea();
}

public class Circulo extends FiguraAbstracta {
    private double radio;

    public Circulo(double radio) { this.radio = radio; }

    @Override
    public double calcularArea() {
        return Math.PI * radio * radio;
    }
}

public class Rectangulo extends FiguraAbstracta {
    private double base;
    private double altura;

    public Rectangulo(double base, double altura) {
        this.base = base;
        this.altura = altura;
    }

    @Override
    public double calcularArea() {
        return base * altura;
    }
}

// Esta clase ya nunca necesita modificarse para soportar figuras nuevas
public class CalculadoraDeArea {
    public double calcular(FiguraAbstracta figura) {
        return figura.calcularArea();
    }
}
```

```java
// Agregar una figura nueva es EXTENDER, no modificar:
public class Triangulo extends FiguraAbstracta {
    private double base;
    private double altura;

    public Triangulo(double base, double altura) {
        this.base = base;
        this.altura = altura;
    }

    @Override
    public double calcularArea() {
        return (base * altura) / 2;
    }
}
```

```java
public class App {
    public static void main(String[] args) {
        CalculadoraDeArea calculadora = new CalculadoraDeArea();

        FiguraAbstracta[] figuras = {
            new Circulo(5),
            new Rectangulo(4, 6),
            new Triangulo(3, 8)   // figura nueva, CalculadoraDeArea no cambió
        };

        for (FiguraAbstracta f : figuras) {
            System.out.println("Área: " + calculadora.calcular(f));
        }
    }
}
```

### Justificación real

Esto es exactamente lo que hace posible que frameworks como Spring o librerías de UI acepten "plugins" sin que tú toques su código fuente: definen una interfaz o clase abstracta, y tú extiendes. Cuando trabajas en equipo, OCP significa que puedes agregar un nuevo método de pago, un nuevo tipo de notificación o un nuevo formato de exportación **sin volver a poner en riesgo** el código que otro compañero ya probó y que está en producción.

## L — Liskov Substitution Principle (LSP)

> **Definición:** si `B` es subclase de `A`, entonces se debe poder usar un objeto de `B` en cualquier lugar donde se espera un objeto de `A`, **sin que el programa se rompa o cambie su comportamiento esperado**.

### El problema

Aquí es donde la relación "es un" que aprendiste en herencia puede engañarte. Volvamos a `Vehiculo`. Supongamos que agregamos `Bicicleta` heredando de `Vehiculo`, porque "una bicicleta es un vehículo":

```java
public class Vehiculo {
    protected String marca;
    protected int velocidadMax;

    public Vehiculo(String marca, int velocidadMax) {
        this.marca = marca;
        this.velocidadMax = velocidadMax;
    }

    public void acelerarConMotor() {
        System.out.println(marca + " acelera usando el motor.");
    }
}

// MAL: Bicicleta "es un" Vehiculo, pero rompe el contrato de la superclase
public class Bicicleta extends Vehiculo {

    public Bicicleta(String marca, int velocidadMax) {
        super(marca, velocidadMax);
    }

    @Override
    public void acelerarConMotor() {
        // Una bicicleta no tiene motor... ¿qué hacemos aquí?
        throw new UnsupportedOperationException("¡Las bicicletas no tienen motor!");
    }
}
```

```java
public class App {
    public static void main(String[] args) {
        Vehiculo[] flota = {
            new Vehiculo("Genérico", 100),
            new Bicicleta("BMX", 30)
        };

        for (Vehiculo v : flota) {
            v.acelerarConMotor();  // esto revienta con Bicicleta
        }
    }
}
```

**¿Por qué es un problema?** El código que usa `flota` (un `for` normal que confía en el contrato de `Vehiculo`) no tiene forma de saber que uno de los elementos va a lanzar una excepción. Cualquier cliente de `Vehiculo` puede romperse sin previo aviso al recibir una `Bicicleta`. La relación "es un" gramaticalmente existía, pero **de comportamiento, no existía**.

### La solución

El problema no es la herencia en sí, es que `Vehiculo` definió un contrato (`acelerarConMotor`) que no todas las subclases pueden cumplir. La solución es reestructurar la jerarquía separando lo que sí es común de lo que no:

```java
// La superclase solo define lo que TODO vehículo cumple sin excepción
public abstract class Vehiculo {
    protected String marca;
    protected int velocidadMax;

    public Vehiculo(String marca, int velocidadMax) {
        this.marca = marca;
        this.velocidadMax = velocidadMax;
    }

    public abstract void acelerar();
}

// Interfaz separada SOLO para vehículos que sí tienen motor
public interface ConMotor {
    void acelerarConMotor();
}

public class Carro extends Vehiculo implements ConMotor {
    public Carro(String marca, int velocidadMax) {
        super(marca, velocidadMax);
    }

    @Override
    public void acelerar() {
        acelerarConMotor();
    }

    @Override
    public void acelerarConMotor() {
        System.out.println(marca + " acelera usando el motor.");
    }
}

// Bicicleta ya no promete algo que no puede cumplir
public class Bicicleta extends Vehiculo {
    public Bicicleta(String marca, int velocidadMax) {
        super(marca, velocidadMax);
    }

    @Override
    public void acelerar() {
        System.out.println(marca + " acelera con pedaleo.");
    }
}
```

```java
public class App {
    public static void main(String[] args) {
        Vehiculo[] flota = {
            new Carro("Toyota", 180),
            new Bicicleta("BMX", 30)
        };

        for (Vehiculo v : flota) {
            v.acelerar();  // cada uno cumple el contrato a su manera, sin excepciones
        }
    }
}
```

### Justificación real

LSP es el principio que más errores silenciosos previene en sistemas grandes. El caso clásico de la literatura es `Cuadrado extends Rectangulo`: matemáticamente un cuadrado es un rectángulo, pero si `setAncho()` y `setAlto()` en `Cuadrado` fuerzan ambos lados a ser iguales, cualquier código que asuma que puede cambiar ancho y alto de forma independiente (como haría con cualquier `Rectangulo`) obtiene resultados inesperados. La lección para el diseño de software real: **la herencia debe modelar comportamiento sustituible, no solo taxonomía del mundo real.** "Es un" en el lenguaje natural no siempre es "es un" en términos de contrato de programación.

## I — Interface Segregation Principle (ISP)

> **Definición:** es mejor tener **varias interfaces pequeñas y específicas** que una sola interfaz grande y genérica. Ninguna clase debería verse obligada a implementar métodos que no usa.

### El problema

Queremos modelar que algunos vehículos vuelan, otros nadan y otros solo andan en tierra. Si creamos una sola interfaz gigante:

```java
// MAL: interfaz "gorda" que obliga a implementar todo, se use o no
public interface Vehiculo {
    void andarEnTierra();
    void volar();
    void navegar();
}

public class Carro implements Vehiculo {
    @Override
    public void andarEnTierra() {
        System.out.println("El carro anda por la carretera.");
    }

    @Override
    public void volar() {
        // Un carro no vuela... ¿qué ponemos aquí?
        throw new UnsupportedOperationException("Un carro no vuela.");
    }

    @Override
    public void navegar() {
        throw new UnsupportedOperationException("Un carro no navega.");
    }
}
```

**¿Por qué es un problema?** `Carro` queda "contaminado" con métodos que no le corresponden y que solo existen para lanzar excepciones. Además, si mañana la interfaz `Vehiculo` agrega un método nuevo (por ejemplo `sumergirse()`), **todas** las clases que la implementan (aunque no les aplique) se ven obligadas a cambiar.

### La solución

Partimos la interfaz grande en varias interfaces pequeñas, cada una representando una capacidad concreta:

```java
// BIEN: interfaces pequeñas y específicas (segregadas)
public interface Terrestre {
    void andarEnTierra();
}

public interface Aereo {
    void volar();
}

public interface Acuatico {
    void navegar();
}

// Cada clase implementa SOLO lo que realmente puede hacer
public class Carro implements Terrestre {
    @Override
    public void andarEnTierra() {
        System.out.println("El carro anda por la carretera.");
    }
}

public class Avioneta implements Aereo, Terrestre {
    @Override
    public void volar() {
        System.out.println("La avioneta está volando.");
    }

    @Override
    public void andarEnTierra() {
        System.out.println("La avioneta rueda por la pista.");
    }
}

// Un vehículo anfibio combina capacidades sin heredar métodos que no usa
public class VehiculoAnfibio implements Terrestre, Acuatico {
    @Override
    public void andarEnTierra() {
        System.out.println("El anfibio anda en tierra.");
    }

    @Override
    public void navegar() {
        System.out.println("El anfibio navega en el agua.");
    }
}
```

### Justificación real

ISP es el principio detrás de por qué las interfaces de Java estándar están tan fragmentadas (`Runnable`, `Comparable`, `Serializable`, `Closeable`, en vez de una sola interfaz `Objeto` con quince métodos). En el mundo real, si defines una interfaz `Repositorio` con `guardar()`, `eliminar()`, `exportarAExcel()` y `enviarPorCorreo()`, cualquier implementación de repositorio simple (por ejemplo, para pruebas) queda forzada a implementar métodos irrelevantes. Interfaces pequeñas permiten que cada clase dependa **solo de lo que necesita**, lo cual también facilita enormemente escribir pruebas unitarias (menos métodos falsos que simular).

## D — Dependency Inversion Principle (DIP)

> **Definición:** los módulos de alto nivel no deben depender de módulos de bajo nivel; ambos deben depender de **abstracciones**. Las abstracciones no deben depender de detalles; los detalles deben depender de abstracciones.

### El problema

Un módulo de "alto nivel" (la lógica del negocio) que depende directamente de una implementación concreta (bajo nivel):

```java
// Módulo de bajo nivel: un detalle concreto de implementación
public class MotorGasolina {
    public void encender() {
        System.out.println("Motor a gasolina encendido.");
    }
}

// MAL: Carro (alto nivel) depende DIRECTAMENTE de MotorGasolina (bajo nivel)
public class Carro {
    private MotorGasolina motor = new MotorGasolina();

    public void arrancar() {
        motor.encender();
    }
}
```

**¿Por qué es un problema?** Si mañana quieres un `Carro` eléctrico, no puedes: `Carro` está "casado" con `MotorGasolina` en tiempo de compilación. Cambiar el tipo de motor obliga a modificar la clase `Carro` (esto además viola OCP). También es imposible probar `Carro` con un motor simulado (mock) en una prueba unitaria, porque el motor real siempre se crea dentro de la clase.

### La solución

Invertimos la dependencia: en vez de que `Carro` dependa de un motor concreto, depende de una **abstracción** (interfaz), y el motor concreto se le entrega desde afuera (esto se llama inyección de dependencias):

```java
// La abstracción de la que dependen TANTO el alto como el bajo nivel
public interface Motor {
    void encender();
}

// Detalles concretos (bajo nivel), dependen de la abstracción Motor
public class MotorGasolina implements Motor {
    @Override
    public void encender() {
        System.out.println("Motor a gasolina encendido.");
    }
}

public class MotorElectrico implements Motor {
    @Override
    public void encender() {
        System.out.println("Motor eléctrico encendido en silencio.");
    }
}

// Carro (alto nivel) depende de la ABSTRACCIÓN Motor, no de un detalle
public class Carro {
    private Motor motor;

    // El motor se "inyecta" desde afuera, vía constructor
    public Carro(Motor motor) {
        this.motor = motor;
    }

    public void arrancar() {
        motor.encender();
    }
}
```

```java
public class App {
    public static void main(String[] args) {
        Carro carroGasolina = new Carro(new MotorGasolina());
        carroGasolina.arrancar();

        Carro carroElectrico = new Carro(new MotorElectrico());
        carroElectrico.arrancar();

        // Cambiar de motor NO requiere tocar la clase Carro
    }
}
```

### Justificación real

Esto es literalmente lo que hacen frameworks de inyección de dependencias como Spring: en vez de que tus clases construyan sus propias dependencias con `new`, reciben abstracciones ya resueltas desde afuera. La ventaja práctica más inmediata es la **capacidad de probar**: en una prueba unitaria de `Carro`, puedes inyectar un `MotorFalso` que simplemente registre si fue llamado, sin necesitar un motor real. Además, DIP es lo que permite que un sistema cambie de proveedor (por ejemplo, de pasarela de pagos, de proveedor de correo, de base de datos) modificando solo la implementación concreta que se inyecta, sin tocar la lógica de negocio.

## Tabla resumen

| Principio | Pregunta que responde | Mecanismo típico en Java |
|---|---|---|
| **S**RP | ¿Esta clase tiene más de una razón para cambiar? | Dividir en clases con una sola responsabilidad |
| **O**CP | ¿Para agregar algo nuevo tengo que modificar código existente? | Clases abstractas / interfaces + polimorfismo |
| **L**SP | ¿Puedo reemplazar la superclase por la subclase sin sorpresas? | Diseñar jerarquías por comportamiento, no solo por taxonomía |
| **I**SP | ¿Estoy obligando a implementar métodos que no se usan? | Interfaces pequeñas y específicas |
| **D**IP | ¿Mi clase depende de un detalle concreto o de una abstracción? | Interfaces + inyección de dependencias |

## Lo que NO es aplicar SOLID

```java
// MAL: crear una interfaz y una clase abstracta para TODO,
// "por si acaso", sin que exista una necesidad real de extensión
public interface IPunto { }
public abstract class PuntoAbstracto implements IPunto { }
public class Punto extends PuntoAbstracto {
    // esta clase nunca tendrá una segunda implementación
}
```

> SOLID no significa "usar interfaces y clases abstractas en todas partes". Aplicar un principio donde no hay un problema real que resolver es sobre-ingeniería, y viola el sentido común que hay detrás de los propios principios (por ejemplo, el mismo SRP: esa complejidad extra ahora es una responsabilidad más que mantener, sin beneficio). La pregunta correcta siempre es: **¿qué problema de mantenibilidad, extensión o prueba estoy resolviendo con este diseño?**

## Ejercicio propuesto para réplica

A continuación tienes el sistema de gestión de pedidos de un restaurante. Es un código que **ya funciona**, pero fue escrito sin pensar en SOLID: a propósito trae incrustada una violación de cada uno de los cinco principios, una por cada clase o método marcado con un comentario `// REVISAR`. Tu trabajo es encontrarlas, entender por qué son un problema real, y refactorizarlas.

```java
// ==========================================================
// Sistema de gestión de pedidos de un restaurante (versión CON violaciones)
// ==========================================================

public class Pedido {

    private String cliente;
    private String tipoCliente; // "REGULAR", "VIP", "EMPLEADO"
    private List<String> platos = new ArrayList<>();
    private List<Double> precios = new ArrayList<>();

    public void agregarPlato(String nombre, double precio) {
        platos.add(nombre);
        precios.add(precio);
    }

    // REVISAR (1): calcula el total Y decide el descuento con un if/else
    // que crece cada vez que el restaurante inventa un tipo de cliente nuevo.
    public double calcularTotal() {
        double subtotal = 0;
        for (double precio : precios) {
            subtotal += precio;
        }

        if (tipoCliente.equals("REGULAR")) {
            return subtotal;
        } else if (tipoCliente.equals("VIP")) {
            return subtotal * 0.9;
        } else if (tipoCliente.equals("EMPLEADO")) {
            return subtotal * 0.5;
        }
        return subtotal;
    }

    // REVISAR (2): Pedido también sabe persistir datos...
    public void guardarEnBaseDeDatos() {
        System.out.println("Conectando a la BD...");
        System.out.println("INSERT INTO pedidos VALUES (...)");
    }

    // REVISAR (2): ...y también sabe imprimir recibos...
    public void imprimirRecibo() {
        ImpresoraTermica impresora = new ImpresoraTermica();
        impresora.imprimir("Recibo de " + cliente + ": $" + calcularTotal());
    }

    // REVISAR (2): ...y también sabe enviar correos. Una sola clase, cuatro trabajos.
    public void enviarCorreoConfirmacion() {
        System.out.println("Enviando correo de confirmación a " + cliente + "...");
    }

    public void setCliente(String cliente) { this.cliente = cliente; }
    public void setTipoCliente(String tipoCliente) { this.tipoCliente = tipoCliente; }
}

class ImpresoraTermica {
    public void imprimir(String texto) {
        System.out.println("[Impresora térmica] " + texto);
    }
}

// --- Métodos de pago ---

abstract class MetodoPago {
    public abstract void cobrar(double monto);
}

class PagoTarjeta extends MetodoPago {
    @Override
    public void cobrar(double monto) {
        System.out.println("Cobrando $" + monto + " con tarjeta.");
    }
}

class PagoEfectivo extends MetodoPago {
    @Override
    public void cobrar(double monto) {
        System.out.println("Cobrando $" + monto + " en efectivo.");
    }
}

// REVISAR (3): esta subclase no puede cumplir lo que promete la superclase.
class PagoPuntosFidelidad extends MetodoPago {
    private double puntosDisponibles = 20.0;

    @Override
    public void cobrar(double monto) {
        if (monto > puntosDisponibles) {
            throw new IllegalStateException("No hay suficientes puntos para cobrar este monto.");
        }
        System.out.println("Cobrando $" + monto + " con puntos de fidelidad.");
    }
}

// --- Personal del restaurante ---

// REVISAR (4): una sola interfaz para roles que no hacen lo mismo.
interface Empleado {
```

### Lo que tienes que entregar

Para cada uno de los cinco puntos marcados con `// REVISAR`, entrega el código **antes** (ya lo tienes arriba) y tu versión **después**, con un párrafo corto explicando qué problema real resuelve el cambio:

1. **SRP** — el método `calcularTotal()` mezcla el cálculo de la suma con la política de descuentos por tipo de cliente. Sepáralos en responsabilidades distintas.
2. **OCP** — `Pedido` concentra persistencia, impresión y envío de correo además de la lógica de la orden. Divide esas responsabilidades en clases separadas, de forma que agregar una nueva forma de notificar (por ejemplo WhatsApp) no implique modificar `Pedido`.
3. **LSP** — `PagoPuntosFidelidad.cobrar()` lanza una excepción que ninguna otra subclase de `MetodoPago` lanza, y el `for` de `App` no tiene forma de anticiparlo. Rediseña la jerarquía para que cualquier `MetodoPago` sea sustituible sin sorpresas (pista: ¿todo pago debería poder cobrar cualquier monto sin restricciones, o el contrato de la superclase necesita ser más honesto?).

5. **DIP** — `Pedido.imprimirRecibo()` crea directamente un `new ImpresoraTermica()`. Si el restaurante quiere imprimir recibos digitales en PDF, hoy tendría que modificar `Pedido`. Invierte la dependencia para que `Pedido` dependa de una abstracción (`Impresora`) y no del detalle concreto.
