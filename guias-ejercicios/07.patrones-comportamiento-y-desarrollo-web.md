# Guía adicional: los patrones de comportamiento y el desarrollo web

## 1. Para qué sirve esta guía

Esta guía es la hermana de "Los patrones GoF y el desarrollo web", pero para los patrones de **comportamiento**. Si los estructurales se reconocen en la forma en que se arman las piezas de una aplicación, los de comportamiento se reconocen en **lo que pasa cuando la aplicación corre**: cómo viaja una petición, cómo se avisa de un cambio, cómo se elige un algoritmo, cómo avanza un pedido de un estado a otro.

Eso los hace especialmente cercanos al desarrollo web, porque un framework es, en buena parte, una colección de estos patrones ya resueltos. Entenderlos ayuda a **leer** un framework (y no solo a usarlo), y es la mejor preparación para el proyecto final.

---

## 2. Dos escalas: diseño de clases y arquitectura

Igual que con los estructurales, conviene empezar por una aclaración de **escala**.

Los patrones GoF son de **diseño de clases**: describen cómo se relacionan **clases y objetos dentro de una aplicación**, con llamadas a métodos en memoria. Los patrones de **arquitectura** (publicación/suscripción con un broker, orquestación de microservicios, CQRS, *event sourcing*, balanceo de carga, máquinas de estado de flujos de trabajo) describen cómo se relacionan **aplicaciones y servicios entre sí**, normalmente por red, y se estudian en cursos posteriores.

| | Patrón de diseño (GoF) | Patrón de arquitectura |
|---|---|---|
| **Dentro de qué** | Una aplicación | Un sistema de varias aplicaciones |
| **Las piezas son** | Clases y objetos | Servicios, colas, procesos |
| **La comunicación es** | Llamadas a métodos en memoria | Mensajes y peticiones por red |
| **Ejemplo** | Observer: `ProductoNotificador` | Publicación/suscripción con un *broker* de mensajes |
| **Dónde se estudia** | Este curso | Cursos futuros |

**La idea clave:** en los patrones de comportamiento el eco arquitectónico es especialmente fuerte, porque la **comunicación** entre objetos se parece mucho a la comunicación entre servicios. Pero al pasar a la red aparecen problemas nuevos que el patrón de clases no tiene: fallos parciales, mensajes que se pierden o se duplican, orden de entrega, latencia. Por eso el patrón de arquitectura casi siempre hace **más cosas** que su pariente GoF.

> Mensaje para el estudiante: si entienden Observer como diseño de clases, cuando lleguen a la mensajería con *brokers* ya sabrán cuál es la idea de fondo. Esta guía muestra el puente, no lo reemplaza.

## 3. Mapa rápido: patrón de comportamiento y su eco en la web

| Patrón GoF (clases) | Dónde se parece en desarrollo web | Pariente a escala de arquitectura |
|---|---|---|
| **Chain of Responsibility** | Filtros de servlets, cadena de filtros de seguridad, *middlewares* | Políticas encadenadas en un API Gateway |
| **Command** | Tareas enviadas a un `ExecutorService`, trabajos en segundo plano, acciones de Redux | Mensajes de comando en colas, la "C" de CQRS |
| **Iterator** | `Iterator`/`Iterable`/`Stream`, `ResultSet`, paginación de APIs | Paginación por cursor, *streaming* de datos |
| **Mediator** | Controlador que coordina vistas y modelo, controlador de un formulario | Orquestador de un flujo entre microservicios |
| **Memento** | Deshacer en editores, borradores guardados, historial de versiones | *Snapshots* y respaldos |
| **Observer** | Eventos del DOM, `@EventListener` de Spring, programación reactiva | Publicación/suscripción con *broker*, *webhooks* |
| **State** | Ciclo de vida de un pedido, estados de una interfaz (cargando, error, listo) | Máquinas de estado de flujos de trabajo (*workflows*, sagas) |
| **Strategy** | `Comparator`, `PasswordEncoder` de Spring Security, estrategias de Passport.js | Algoritmos de balanceo de carga intercambiables |
| **Template Method** | `HttpServlet`, métodos de ciclo de vida de un framework | Los propios frameworks (inversión de control) |
| **Visitor** | Recorrido del árbol sintáctico en compiladores y linters, `FileVisitor` | (se mantiene dentro de la aplicación) |
| **Interpreter** | Lenguajes de consulta y de expresiones, filtros de búsqueda | Lenguajes específicos de dominio (DSL), motores de reglas |

## 4. Patrón por patrón

### 4.1 Chain of Responsibility

**En el código de la clase:** `ManejadorAutenticacion`, `ManejadorAutorizacion` y `ManejadorLimite` encadenados.

**En desarrollo web:**
- **Los filtros de servlets** y **la cadena de filtros de seguridad** de un framework como Spring Security son este patrón casi literalmente: la petición pasa por una cadena de filtros y cada uno decide si la deja continuar.
- **Los *middlewares* de Express** (y de la mayoría de frameworks web): cada uno recibe la petición y decide si llama a `next()` o corta la cadena respondiendo directamente.
- **Interceptores** en un framework MVC: se ejecutan antes y después del controlador.

```java
// Ilustrativo: un filtro de servlet. Llamar a chain.doFilter(...) es "pasar al siguiente eslabon".
public class FiltroRegistro implements Filter {

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        System.out.println("Llego una peticion");
        chain.doFilter(req, res);          // si no se llama, la cadena se corta aqui
        System.out.println("Ya se respondio");
    }
}
```

**A escala de arquitectura:** un API Gateway aplica una cadena de políticas a cada petición (autenticación, límite de peticiones, registro) antes de enviarla al servicio.

**Una aclaración útil:** el patrón relacionado "tuberías y filtros" (*pipes and filters*) se parece, pero en él **todas** las etapas procesan los datos en orden. En la cadena de responsabilidad, **cualquier eslabón puede detener** el flujo.

### 4.2 Command

**En el código de la clase:** `ComandoEscribir` y `ComandoBorrar` con `ejecutar()` y `deshacer()`.

**En desarrollo web:**
- **`Runnable` y `Callable`** enviados a un `ExecutorService`: la tarea es un objeto que se puede guardar, programar y ejecutar más tarde.
- **Trabajos en segundo plano** (envío de correos, generación de reportes): se encolan como objetos que describen qué hacer.
- **Acciones de Redux:** son objetos que describen "lo que se quiere hacer", y se suelen comparar con el patrón Command.
- **Deshacer y rehacer** en cualquier editor en línea.

**A escala de arquitectura:** en una cola de mensajes, un mensaje de tipo "comando" (por ejemplo "procesar este pago") es la misma idea serializada y enviada por red. En **CQRS** se separan los **comandos** (cambian el sistema) de las **consultas** (solo leen).

**Cuidado:** si la acción nunca se guardará, encolará ni deshará, un comando es sobreingeniería. En Java, a veces basta una lambda.

### 4.3 Iterator

**En el código de la clase:** `ListaReproduccion` con tres iteradores.

**En desarrollo web:**
- **`Iterator`, `Iterable` y `Stream`** de Java: recorrer cualquier colección con el `for` mejorado o con operaciones de flujo.
- **`ResultSet` de JDBC:** el cursor sobre el resultado de una consulta (`while (rs.next())`) es un iterador: no se cargan todas las filas en memoria a la vez.
- **Paginación de una API:** el cliente pide "la siguiente página" sin saber cómo está guardada la información en el servidor.
- **`for...of` y generadores** en JavaScript.

**A escala de arquitectura:** la paginación por **cursor** (el servidor devuelve un marcador para pedir el siguiente grupo) y el *streaming* de datos extienden la idea a través de la red.

**Cuidado:** no crees un iterador propio si el del lenguaje basta.

### 4.4 Mediator

**En el código de la clase:** `SalaChat` coordina a los `Usuario` sin que se conozcan entre sí.

**En desarrollo web:**
- **El controlador de una arquitectura MVC** coordina entre la vista y el modelo, de modo que ninguno conoce al otro.
- **El controlador de un formulario complejo:** cuando un campo cambia, el controlador decide qué otros campos habilitar, ocultar o recalcular, en lugar de que cada campo conozca a los demás.
- **Un bus de eventos de la interfaz** o el **almacén central de estado** (por ejemplo, el de Redux) reducen el acoplamiento entre componentes que, de otro modo, se hablarían directamente.

**A escala de arquitectura:** en un flujo entre microservicios, un **orquestador** central que llama a cada servicio en orden y decide qué sigue se parece a un mediador. Su contraparte, la **coreografía** (cada servicio reacciona a eventos sin coordinador central), se parece más a Observer. Son dos formas opuestas de coordinar, y cada una tiene ventajas y riesgos.

**Cuidado:** el mediador puede crecer hasta saber demasiado ("objeto dios"). Lo mismo le puede pasar a un orquestador.

### 4.5 Memento

**En el código de la clase:** `EditorTexto` guarda `Instantanea` que solo él puede leer.

**En desarrollo web:**
- **Deshacer en editores en línea** y **borradores guardados automáticamente.**
- **Historial de versiones** de un documento: cada versión es una instantánea del estado.
- **Borradores de un formulario largo**, guardados para no perder lo escrito.
- **Puntos de restauración y transacciones** que se pueden revertir (*rollback*) a un estado anterior.

**A escala de arquitectura:** los *snapshots* y respaldos de bases de datos y servidores. Con *event sourcing*, el estado se reconstruye a partir de los eventos y a veces se guardan instantáneas para no tener que repasarlos todos.

**Cuidado:** guardar copias completas con mucha frecuencia consume mucha memoria; se suele guardar solo lo que cambió.

### 4.6 Observer

**En el código de la clase:** `ProductoNotificador` avisa a `SuscriptorCorreo` y `SuscriptorApp`.

**En desarrollo web:**
- **Los eventos del DOM:** `boton.addEventListener("click", ...)` registra un suscriptor en un botón (el notificador).
- **Los eventos de aplicación de Spring:** una clase publica un evento y otras lo escuchan sin conocerse.
- **Programación reactiva** (RxJS, Reactor): un flujo de datos al que uno se suscribe.
- **Actualizaciones en tiempo real** con WebSockets o eventos enviados por el servidor.

```java
// Ilustrativo: eventos de aplicacion en Spring. El servicio no conoce a quien escucha.
public record PedidoCreado(long pedidoId) { }

@Service
public class PedidoServicio {
    private final ApplicationEventPublisher eventos;

    public PedidoServicio(ApplicationEventPublisher eventos) {
        this.eventos = eventos;
    }

    public void crear(long id) {
        // ... guardar el pedido ...
        eventos.publishEvent(new PedidoCreado(id));   // avisa a todos los suscriptores
    }
}

@Component
public class NotificadorCorreo {
    @EventListener
    public void alCrearseUnPedido(PedidoCreado evento) {
        System.out.println("Enviando correo del pedido " + evento.pedidoId());
    }
}
```

**A escala de arquitectura:** la **publicación/suscripción** con un *broker* de mensajes (colas y temas), y los ***webhooks*** (un sistema avisa a otro con una petición HTTP cuando algo ocurre).

**Diferencia a tener presente:** en Observer el notificador **guarda la lista** de suscriptores y los conoce por su interfaz. En la mensajería con un *broker*, publicador y suscriptor **no se conocen en absoluto**: el broker se interpone, y además aparecen problemas de red (mensajes perdidos, duplicados, orden).

### 4.7 State

**En el código de la clase:** `Documento` pasa de `Borrador` a `EnRevision` a `Publicado`.

**En desarrollo web:**
- **El ciclo de vida de un pedido** en una tienda en línea (pendiente, pagado, enviado, entregado, cancelado): lo que se puede hacer depende del estado actual.
- **Los estados de una interfaz:** cargando, con error, con datos. Cada uno muestra algo distinto.
- **Una sesión de usuario** (anónima, autenticada, expirada).
- Los **estados de una conexión** de red, en bajo nivel.
- En frameworks como Spring existen bibliotecas de **máquinas de estado** para este fin.

**A escala de arquitectura:** los **motores de flujos de trabajo** (*workflows*) y las **sagas** (secuencias de pasos entre servicios con compensaciones) son máquinas de estado distribuidas.

**Cuidado:** con pocos estados y transiciones obvias, un `enum` con un `switch` es más simple.

### 4.8 Strategy

**En el código de la clase:** `EnvioEstandar`, `EnvioExpress`, `RecogerEnTienda` intercambiables.

**En desarrollo web:**
- **`Comparator`** pasado a `list.sort(...)`: la forma de ordenar es una estrategia.
- **`PasswordEncoder` en Spring Security:** el código depende de la interfaz y se elige la implementación (`BCryptPasswordEncoder`, por ejemplo) por configuración.
- **Passport.js** ni siquiera disimula el patrón: llama "estrategias" a cada forma de autenticarse (usuario y contraseña, Google, etc.).
- **Elegir la pasarela de pago, el cálculo de impuestos o de envío** según el país o el cliente.

```java
// Ilustrativo: el servicio depende de la interfaz, no de una implementacion concreta.
@Service
public class RegistroServicio {
    private final PasswordEncoder codificador;       // la estrategia

    public RegistroServicio(PasswordEncoder codificador) {
        this.codificador = codificador;              // el framework inyecta la que se configure
    }

    public String guardarClave(String clave) {
        return codificador.encode(clave);
    }
}
```

**A escala de arquitectura:** los **algoritmos de balanceo de carga** (por turnos, menos conexiones, etc.) que un balanceador permite cambiar por configuración.

**Una pista del proyecto final:** la **inyección de dependencias** de un framework es, en la práctica, una máquina para elegir qué estrategia usa cada clase, sin que la clase lo decida.

### 4.9 Template Method

**En el código de la clase:** `GeneradorReporte.generar()` fija el flujo y `ReporteCsv` y `ReporteHtml` rellenan pasos.

**En desarrollo web:**
- **`HttpServlet`:** el servidor decide cuándo llamar a `doGet` o `doPost` y tú solo los implementas.
- **Los métodos de ciclo de vida** de componentes en los frameworks (inicializar, montar, destruir).
- **Las bibliotecas de pruebas** como JUnit: el marco decide el orden (preparar, ejecutar, limpiar) y tú escribes cada paso.

```java
// Ilustrativo: HttpServlet es la clase base con el esqueleto; tu clase rellena un paso.
public class ProductosServlet extends HttpServlet {

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        resp.getWriter().println("Lista de productos");
    }
}
```

**A escala de arquitectura:** este patrón es la idea que hay detrás de los **frameworks** en general: la inversión de control o "principio de Hollywood" ("no nos llames, nosotros te llamamos"). La biblioteca no es algo que tú llamas, sino algo que **te llama a ti** en los momentos adecuados.

**Una pista del proyecto final:** cuando trabajen con un framework, buena parte de lo que escriban serán precisamente "pasos" que el framework invoca.

### 4.10 Visitor

**En el código de la clase:** `VisitanteImpuestos` y `VisitanteDescripcion` recorren elementos del carrito.

**En desarrollo web y en Java:**
- **Compiladores, transpiladores y *linters*:** recorren el árbol sintáctico de un programa con visitantes (es el uso más típico del patrón). Herramientas como Babel o ESLint se apoyan en esta idea para que escribas reglas que "visitan" ciertos tipos de nodo.
- **`FileVisitor` de Java** (`Files.walkFileTree`): recorre un árbol de carpetas y archivos llamando a un visitante por cada elemento.
- **Recorrido de documentos estructurados** (HTML, XML) para extraer o transformar partes.

**A escala de arquitectura:** no tiene un pariente claro; es un patrón de organización del código dentro de la aplicación.

**Cuidado:** si las clases de elementos cambian con frecuencia, cada una nueva obliga a modificar todos los visitantes. En Java moderno, el *pattern matching* con `switch` sobre interfaces selladas puede resolverlo con menos código.

### 4.11 Interpreter

**En el código de la clase:** `Suma`, `Resta`, `Variable`... forman un árbol que se evalúa con `interpretar(contexto)`.

**En desarrollo web:**
- **Lenguajes de consulta y filtros:** una API que acepta `?filtro=precio>100 AND stock>0` necesita interpretar ese texto.
- **Lenguajes de expresiones** de frameworks (por ejemplo, el de Spring o los de las plantillas HTML) que evalúan expresiones escritas en texto.
- **Expresiones regulares, SQL o GraphQL:** son lenguajes pequeños que alguien tuvo que interpretar; en la práctica se implementan con generadores de analizadores y bibliotecas, no a mano.
- **Motores de reglas de negocio** configurables sin recompilar.

**A escala de arquitectura:** los **lenguajes específicos de dominio** (DSL) y los motores de reglas: la regla es un dato que el sistema evalúa.

**Cuidado:** para gramáticas grandes, el patrón no escala: se usan generadores de analizadores. Es de los patrones que menos se escriben a mano en el día a día.

## 5. Mapa para el proyecto final: patrones de los tres tipos en una aplicación web

Si el proyecto final es una aplicación web con un framework, estos son los lugares donde los patrones aparecen de forma natural. Sirve como lista de ideas para decidir qué implementar, y como lista de preguntas para sustentar.

| Parte de la aplicación | Patrón que encaja | Tipo |
|---|---|---|
| Un componente único compartido (por ejemplo, la configuración) | **Singleton** (los componentes del framework suelen ser únicos por defecto) | Creacional |
| Objetos de petición o de respuesta con muchos campos opcionales | **Builder** | Creacional |
| Elegir qué implementación crear según el contexto | **Factory Method** | Creacional |
| Consumir una API de un tercero con otro formato | **Adapter** | Estructural |
| Una capa de servicios que coordina varios repositorios | **Facade** | Estructural |
| Caché, transacciones o seguridad alrededor de un servicio | **Proxy** | Estructural |
| Agregar comportamientos apilables (registro, validación) | **Decorator** | Estructural |
| Filtros de seguridad, validaciones en cadena | **Chain of Responsibility** | Comportamiento |
| Cálculo de precios, envíos o impuestos intercambiables | **Strategy** | Comportamiento |
| Avisar a otras partes cuando algo ocurre (correo al crear un pedido) | **Observer** | Comportamiento |
| Ciclo de vida de un pedido o de un documento | **State** | Comportamiento |
| Flujos con pasos fijos y detalles variables | **Template Method** | Comportamiento |
| Tareas en segundo plano, deshacer | **Command** | Comportamiento |

Una forma de usarla: pedir que el proyecto incluya **al menos un patrón de cada tipo**, que cada uno resuelva un problema real de la aplicación (y no esté ahí "porque sí"), y que el equipo pueda explicar qué pasaría **sin** el patrón.

## 6. Preguntas para la discusión en clase

1. Los filtros de seguridad de un framework web, ¿son una cadena de responsabilidad o una tubería? ¿Qué pasa cuando un filtro rechaza la petición?
2. ¿En qué se parece un *broker* de mensajes a un Observer y en qué se diferencia? (Pista: ¿el publicador conoce a los suscriptores?)
3. Un orquestador de microservicios y un mediador de clases hacen algo parecido. ¿Qué riesgo comparten?
4. ¿Por qué se dice que un framework "te llama a ti" y no al revés? ¿Qué patrón explica eso?
5. En una tienda en línea, ¿el cálculo de envío debería ser Strategy o State? ¿Y el ciclo de vida del pedido? ¿Por qué?
6. ¿Por qué un linter es un caso natural para Visitor, mientras que un carrito de compras con pocos tipos de producto quizá no lo necesita?

---

## 7. Resumen para llevarse

- Los patrones de comportamiento describen **lo que pasa mientras el programa corre**: cómo viaja una petición, cómo se avisa de un cambio, cómo se elige un algoritmo.
- Los frameworks web están construidos sobre ellos: Chain of Responsibility en los filtros, Observer en los eventos, Strategy en la inyección de dependencias, Template Method en la inversión de control.
- Los patrones de **arquitectura** (publicación/suscripción, orquestación, CQRS, sagas) son el mismo concepto a otra escala, pero con problemas de red que el patrón de clases no tiene.
- Para el proyecto final: un patrón se justifica por **el problema que resuelve**, no por aparecer en el catálogo.
