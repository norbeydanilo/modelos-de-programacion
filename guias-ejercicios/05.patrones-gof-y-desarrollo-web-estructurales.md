# Guía adicional: los patrones GoF y el desarrollo web

## 1. Para qué sirve esta guía

Cuando los estudiantes ven Adapter, Facade o Proxy por primera vez, suelen preguntar "¿y esto dónde lo voy a usar?". La respuesta honesta es: **ya lo están usando**, porque buena parte de las herramientas del desarrollo web (frameworks, servidores, bibliotecas) están construidas con estos patrones.

Esta guía conecta los patrones que vemos en clase con cosas que los estudiantes reconocen del mundo web. Pero antes de hacerlo hay una aclaración importante sobre **escala**, para que no se confundan conceptos que se parecen.

---

## 2. Dos escalas: diseño de clases y arquitectura

Los 23 patrones del catálogo GoF son patrones de **diseño de clases**: describen cómo se relacionan **clases y objetos dentro de una aplicación**. Lo que se resuelve con ellos cabe en un proyecto de Java.

Existe otro nivel, el de los patrones de **arquitectura**, que describen cómo se relacionan **aplicaciones, servicios y componentes entre sí**, normalmente comunicados por red. Ejemplos: API Gateway, Backend for Frontend (BFF), proxy inverso, microservicios, CQRS, Event Sourcing. Estos **no son parte del GoF** y se estudian en cursos posteriores.

| | Patrón de diseño (GoF) | Patrón de arquitectura |
|---|---|---|
| **Dentro de qué** | Una aplicación | Un sistema de varias aplicaciones |
| **Las piezas son** | Clases y objetos | Servicios, procesos, servidores |
| **La comunicación es** | Llamadas a métodos en memoria | Peticiones por red (HTTP, mensajes) |
| **Ejemplo** | Facade: `TiendaFachada` | API Gateway |
| **Dónde se estudia** | Este curso | Cursos futuros (arquitectura de software, microservicios) |

**La idea clave:** muchos patrones de arquitectura son la **misma idea** de un patrón GoF, aplicada a mayor escala. Un API Gateway se parece a un Facade, y un proxy inverso se parece a un Proxy. Esa semejanza ayuda a entenderlos, pero **no son lo mismo**: cambian las preocupaciones (latencia, fallos de red, seguridad, escalamiento), y el patrón de arquitectura casi siempre hace **más cosas** que su pariente GoF.

> Mensaje para el estudiante: si entienden bien Facade como diseño de clases, cuando lleguen a API Gateway ya tendrán la mitad del concepto. Esta guía muestra ese puente, no lo reemplaza.

---

## 3. Mapa rápido: patrón estructural y su eco en la web

| Patrón GoF (clases) | Dónde se parece en desarrollo web | Pariente a escala de arquitectura |
|---|---|---|
| **Adapter** | Clientes de APIs externas, mappers y DTOs, `InputStreamReader` | Capa anticorrupción (*anti-corruption layer*) |
| **Bridge** | JDBC y sus controladores, servicios con "canales" intercambiables | Arquitectura hexagonal (puertos y adaptadores) |
| **Composite** | El DOM, el árbol de componentes de React, menús anidados | (se mantiene dentro de la aplicación) |
| **Decorator** | Entrada/salida de Java, decoradores de TypeScript y Python, componentes de orden superior (HOC) en React | *Sidecar* (proceso que "envuelve" a un servicio) |
| **Facade** | Capa de servicios, SDKs, `fetch` sobre `XMLHttpRequest`, jQuery | **API Gateway**, Backend for Frontend |
| **Flyweight** | Pool de cadenas de Java, caché de `Integer`, hojas de sprites | (se mantiene dentro de la aplicación) |
| **Proxy** | Spring (`@Transactional`, `@Cacheable`), carga diferida de Hibernate, `Proxy` de JavaScript | **Proxy inverso** (Nginx), CDN, balanceador de carga |

## 4. Patrón por patrón

### 4.1 Adapter

**En el código de la clase:** `AdaptadorPasarelaLegada` traduce pesos a centavos y el texto `"OK-..."` a `boolean`.

**En desarrollo web:**
- **Cliente de una API externa.** Tu aplicación consume una API de terceros (pagos, mapas, mensajería) que devuelve JSON con su propio formato. Escribes una clase que recibe esa respuesta y la convierte al modelo de **tu** dominio. Si el proveedor cambia o lo reemplazas, solo cambia el adaptador.
- **Mappers y DTOs.** Convertir una entidad de la base de datos en el objeto que se envía al front. Es una traducción de formato entre dos mundos que no deben conocerse.
- **Un clásico dentro de Java:** `InputStreamReader` adapta un `InputStream` (bytes) a un `Reader` (caracteres).

```java
// Ilustrativo: un adaptador entre la respuesta de un proveedor externo y el modelo propio
public class AdaptadorClimaProveedorX implements ServicioClima {

    private final ClienteProveedorX cliente;   // clase del tercero, no la controlamos

    public AdaptadorClimaProveedorX(ClienteProveedorX cliente) {
        this.cliente = cliente;
    }

    @Override
    public double temperaturaCelsius(String ciudad) {
        double kelvin = cliente.consultarTemperaturaKelvin(ciudad);   // el proveedor responde en kelvin
        return kelvin - 273.15;                                       // nuestro dominio trabaja en celsius
    }
}
```

**A escala de arquitectura:** la *capa anticorrupción* es la misma idea entre sistemas: una capa que traduce entre un sistema externo (o heredado) y el tuyo para que sus conceptos no "contaminen" tu modelo.

**Cuidado:** si controlas ambas partes, normalmente basta con cambiar una; el adaptador sobra.

### 4.2 Bridge

**En el código de la clase:** `Notificacion` (normal o urgente) separada de `Canal` (correo, SMS o push).

**En desarrollo web:**
- **JDBC** es un ejemplo muy claro: tu código usa una interfaz común (`Connection`, `Statement`) y cada motor de base de datos aporta su controlador (*driver*). La API y las implementaciones **evolucionan por separado**, y puedes cambiar de MySQL a PostgreSQL cambiando el controlador.
- **Servicios con canales o proveedores intercambiables:** envío de correos (SMTP, un servicio externo), almacenamiento (disco local, nube).

**A escala de arquitectura:** la *arquitectura hexagonal* (puertos y adaptadores) lleva la misma separación al sistema completo: el núcleo del negocio habla con "puertos" (interfaces) y cada tecnología concreta se conecta mediante un adaptador.

**Cuidado:** Bridge se aplica al **diseñar**, cuando ya se ve que habrá dos dimensiones de variación. No es un patrón para arreglar código existente.

### 4.3 Composite

**En el código de la clase:** `Archivo` y `Carpeta` bajo la interfaz `ElementoArchivo`.

**En desarrollo web:**
- **El DOM de una página:** un elemento HTML puede contener otros elementos, a cualquier profundidad, y se puede aplicar la misma operación (ocultar, mover, borrar) a uno solo o a todo un subárbol.
- **El árbol de componentes de React** (o de cualquier framework de interfaces): un componente puede contener otros componentes.
- **Menús y categorías anidadas** de una tienda en línea, con subcategorías de profundidad variable.
- **Interfaces gráficas de Java** (Swing, JavaFX): un contenedor guarda componentes, que a su vez pueden ser contenedores.

**A escala de arquitectura:** este patrón suele mantenerse **dentro de la aplicación**; no tiene un pariente arquitectónico claro.

**Cuidado:** solo vale la pena si el modelo es realmente un árbol.

### 4.4 Decorator

**En el código de la clase:** `Crema(Leche(Leche(Cafe)))`.

**En desarrollo web:**
- **La entrada y salida de Java:** `new BufferedReader(new InputStreamReader(new FileInputStream("datos.txt")))`. Cada capa agrega una capacidad (puente de bytes a caracteres, buffer) y se apilan en tiempo de ejecución.
- **Componentes de orden superior (HOC) en React:** una función que recibe un componente y devuelve otro con comportamiento adicional (por ejemplo, exigir que el usuario esté autenticado).
- **Decoradores de TypeScript o de Python:** funciones que envuelven a otra para agregarle registro de eventos, validación o caché.

**Una aclaración honesta sobre los *middlewares*.** Los middlewares de Express o los filtros de servlets de Java se suelen citar como ejemplos de Decorator, pero técnicamente se parecen más al patrón **Chain of Responsibility** (patrón de comportamiento, lo veremos después): una petición pasa por una cadena de manejadores y cada uno decide si continúa. Visualmente se parecen a capas apiladas, y por eso se confunden.

**A escala de arquitectura:** el modelo *sidecar*, donde un proceso acompaña a un servicio y le agrega funciones (seguridad, registro, métricas) sin modificarlo, es la misma idea llevada a nivel de procesos.

**Cuidado:** con muchas capas pequeñas, depurar cuesta; y el orden de apilado puede cambiar el resultado.

### 4.5 Facade

**En el código de la clase:** `TiendaFachada.comprar()` coordina inventario, pago, envío y correo.

**En desarrollo web:**
- **La capa de servicios de una aplicación** (por ejemplo, una clase `@Service` en Spring): el controlador llama un método y la capa de servicios coordina varios repositorios y reglas de negocio.
- **SDKs y bibliotecas cliente** (de AWS, Stripe, Firebase): ocultan decenas de llamadas HTTP detrás de métodos como `subirArchivo()`.
- **`fetch` frente a `XMLHttpRequest`**, o **jQuery frente al DOM**: una interfaz más simple sobre una API más pesada.

**A escala de arquitectura:**
- El **API Gateway** es una fachada para un sistema de microservicios: un único punto de entrada que oculta los servicios internos. Con una sola llamada, el cliente obtiene lo que de otra forma requeriría hablar con varios servicios.
- El **Backend for Frontend (BFF)** es una variante: un gateway diseñado específicamente para un tipo de cliente (móvil, web), que arma las respuestas a la medida de cada pantalla.

**Diferencia a tener presente:** un API Gateway hace más que una fachada clásica: autenticación, límite de peticiones, balanceo, caché. En esas funciones ya se parece más a un Proxy. La parte de "un único punto de entrada que orquesta" es la que corresponde a Facade.

**Cuidado:** que la fachada no se convierta en un "objeto dios". Lo mismo aplica a un gateway que acumula demasiada lógica de negocio.

### 4.6 Flyweight

**En el código de la clase:** 10.000 árboles compartiendo 3 objetos `TipoArbol`.

**En desarrollo web y en Java:**
- **El pool de cadenas de Java** (`String.intern()` y los literales): textos iguales comparten el mismo objeto en memoria.
- **La caché de `Integer`:** `Integer.valueOf(100)` devuelve siempre el mismo objeto para valores entre -128 y 127.
- **Hojas de sprites y texturas compartidas** en videojuegos y gráficos 2D: una sola imagen en memoria, usada en muchos lugares con posición propia.

**Una distinción que suele confundirse:** el **pool de conexiones** a la base de datos **no es Flyweight**, es otro patrón (*Object Pool*, que no está en el catálogo GoF). La diferencia es que Flyweight comparte estado **inmutable** entre muchos usuarios **a la vez**, mientras que un pool **presta** un objeto a un usuario por vez y luego lo recupera.

**A escala de arquitectura:** no tiene un pariente claro; es un patrón de optimización de memoria dentro de una aplicación.

**Cuidado:** es una optimización. Se aplica después de medir, no antes.

### 4.7 Proxy

**En el código de la clase:** `ImagenProxy` carga la imagen solo cuando se necesita.

**En desarrollo web:**
- **Spring** crea proxies automáticamente alrededor de tus clases: cuando anotas un método con `@Transactional` o `@Cacheable`, lo que recibes no es tu objeto directamente sino un proxy que abre la transacción o consulta la caché **antes** de delegar en tu método.
- **Carga diferida (*lazy loading*) de Hibernate/JPA:** una relación no se consulta a la base de datos hasta que se usa; mientras tanto, lo que hay en memoria es un proxy.
- **El objeto `Proxy` de JavaScript:** permite interceptar la lectura y escritura de propiedades de otro objeto.

```java
// Ilustrativo: para el programador es una clase normal; Spring la envuelve en un proxy
@Service
public class CatalogoServicio {

    @Cacheable("productos")                       // el proxy consulta la cache ANTES de ejecutar el metodo
    public Producto buscarPorId(long id) {
        return repositorio.findById(id);          // solo se ejecuta si la cache no tiene la respuesta
    }
}
```

**A escala de arquitectura:** el **proxy inverso** (Nginx, por ejemplo), una **CDN** o un **balanceador de carga** están delante de los servidores reales, reciben las peticiones y deciden cómo y a quién delegarlas, con la misma lógica: mismo "idioma" hacia el cliente, control adicional en el medio.

**Cuidado:** si lo que buscas es agregar funcionalidades apilables, el patrón es Decorator. Proxy se centra en **controlar el acceso**.

## 5. Bonus: los patrones creacionales en la web

| Patrón | Dónde aparece |
|---|---|
| **Singleton** | Los *beans* de Spring son singleton por defecto: una sola instancia por contenedor |
| **Factory Method** | `Calendar.getInstance()`, `DriverManager.getConnection(...)`, las fábricas de objetos de los frameworks |
| **Abstract Factory** | `DocumentBuilderFactory` y otras fábricas de familias de objetos relacionados |
| **Builder** | `StringBuilder`, `HttpRequest.newBuilder()`, `@Builder` de Lombok, constructores de consultas |
| **Prototype** | El alcance *prototype* de Spring, que crea un objeto nuevo en cada solicitud; `clone()` en Java |

## 6. Preguntas para la discusión en clase

1. En su proyecto, ¿qué clase actúa como fachada entre la interfaz y la lógica de negocio? ¿Qué pasaría si no existiera?
2. Piensen en una API de terceros que hayan consumido. ¿Dónde está (o debería estar) el adaptador?
3. ¿Cuál es la diferencia entre un Decorator y un Proxy, si ambos envuelven a un objeto con su misma interfaz?
4. Un API Gateway y un Facade se parecen, pero no son lo mismo. ¿Qué responsabilidades adicionales tiene el gateway que el Facade de la clase no tiene?
5. ¿Por qué un pool de conexiones no es un Flyweight?

---

## 7. Resumen para llevarse

- Los patrones GoF son de **diseño de clases**; los de **arquitectura** (API Gateway, BFF, proxy inverso, hexagonal) son de otro nivel y se verán en cursos posteriores.
- Muchos patrones de arquitectura son el **mismo concepto a otra escala**: entender el patrón pequeño ayuda a entender el grande.
- La semejanza no es identidad: **el patrón de arquitectura casi siempre hace más cosas** y enfrenta problemas nuevos (red, fallos, seguridad).
- Un envoltorio no es siempre el mismo patrón: la **intención** (traducir, agregar, simplificar, controlar) es lo que los distingue.
